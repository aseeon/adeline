# Extension UI without arbitrary UI code: host-rendered cards, widgets and native extension UI (as of Oct 2026)

Scope: how third parties contribute UI to a host app, with schema details, to inform Adeline (Rust GPUI native app for ACP coding agents) where a mode (Docs, Issues) renders rich cards in the chat transcript that open a full view on click.

## 1. Host-rendered card schemas (Slack, Adaptive Cards, Discord, Teams/Outlook, Google Chat)

### Takeaway
Every major chat platform converged on the same shape: a JSON tree from a closed vocabulary (text, image, fact list, button row, inputs), a small action set (open URL, post back to the app with an id/value, open a dialog/sub-view), and hard size/count limits. The host draws it with its own theme. Slack's 2025-26 additions (a dedicated `card` block, and Work Objects with an unfurl card plus a "flexpane" detail view) are almost exactly the "card in transcript, click opens full view" model Adeline wants.

### Cited Findings

**Slack Block Kit**
- Block catalogue now lists 21 block types: Actions, Alert, Card, Carousel, Container, Context, Context actions, Data table, Data visualization (pie/bar/area/line charts), Divider, File, Header, Image, Input, Markdown, Plan, Rich text, Section, Table, Task card, Video. Limits: up to 50 blocks per message, 100 in modals/Home tabs. The page carries no dates, so which ones are 2025-26 additions could not be confirmed (Card, Carousel, Alert, Plan, Task card, Data table, Data visualization were not in older Block Kit). — [Slack blocks reference](https://docs.slack.dev/reference/block-kit/blocks)
- `card` block schema: `type: "card"`, `block_id`, `hero_image` (image element, URL <= 3000 chars, alt_text <= 2000), `icon` (image) or `slack_icon` (mutually exclusive), `title` (<= 150 chars, plain_text or mrkdwn), `subtitle` (<= 150), `body` (<= 200), `subtext` (<= 200), `actions` (actions block, up to 3 buttons; `danger` left-aligned, `primary` furthest right). At least one of hero_image/title/actions/body required. Usable in messages, modals, Home tabs. No size attribute. — [Slack card block](https://docs.slack.dev/reference/block-kit/blocks/card-block)
- Link unfurling flow: app registers up to 5 "App unfurl domains"; scopes `links:read`/`links:write`; Slack sends `link_shared` event (channel, `message_ts`, `links` array, no message text); app replies with `chat.unfurl` (`channel`, `ts`, `unfurls` = map of URL -> `{blocks}`). Buttons in unfurls send payloads with `app_unfurl` and `is_app_unfurl: true`. Composer unfurls: event with `source: "composer"`, `unfurl_id` instead of ts. Auth-gated unfurls: `user_auth_required`, `user_auth_url`, `user_auth_message`/`user_auth_blocks`. `link_shared` is not sent for app/bot messages. `chat.unfurl` rejects rich_text blocks. Fallback when no app owns the domain: Slack crawls OpenGraph / X Card metadata. Slack recommends considering disabling unfurls on LLM-generated messages to reduce data-exfiltration risk via prompt injection. — [Slack unfurling](https://docs.slack.dev/messaging/unfurling-links-in-messages)
- Work Objects: entities other than conversations (files, tasks, incidents) get a standard presentation. Two surfaces: an **unfurl** component (visible to everyone in the channel, no sensitive data) and a **flexpane** that opens on the right when the unfurl is clicked (can require third-party auth, shows sensitive details, lists related conversations, can host a sandboxed-iframe "embed"). Metadata: `metadata: { entities: [...] }` with `entity_type`, `app_unfurl_url`, `url`, `external_ref` (must be stable; used to track related conversations), `entity_payload`. Events: `link_shared` -> `chat.unfurl` with entity metadata; `entity_details_requested` (user opened flexpane) -> `entity.presentDetails` with `trigger_id`; edits arrive as `view_submission` with callback `work-object-edit`. Work Objects also open from Enterprise Search results, citations and AI answers. Intro date not stated on the page. — [Slack Work Objects](https://docs.slack.dev/messaging/work-objects-overview)

**Microsoft Adaptive Cards (Teams, Outlook, Copilot)**
- Structure: `AdaptiveCard` root with `version`, `body` (elements stack vertically, full width), `actions` (rendered as an action bar). Elements: TextBlock, Image; containers: Container, ColumnSet/Column, FactSet, ImageSet; inputs: Input.Text/Date/Time/Number/ChoiceSet/Toggle; actions: Action.OpenUrl, Action.ShowCard (inline sub-card), Action.Submit (gathers inputs, delivered "through some method defined by the host"). — [Adaptive Cards getting started](https://learn.microsoft.com/en-us/adaptive-cards/authoring-cards/getting-started)
- Universal Action Model: `Action.Execute` and `refresh` require schema >= 1.4; `refresh.userIds` limits which users auto-refresh in Teams, Outlook always honors refresh; schema 1.6 adds an expiry timestamp on Refresh. — [Outlook Universal Action Model](https://learn.microsoft.com/en-us/outlook/actionable-messages/universal-action-model); [Schema Explorer: Refresh](https://adaptivecards.io/explorer/Refresh.html)
- Teams supports Adaptive Card features up to v1.6 (bots, message extensions, link unfurling, dialogs, mobile); positive/destructive action styling unsupported; no file/image upload in cards; images max 1024x1024, PNG/JPEG/GIF (no animated GIF or SVG); hero/thumbnail cards max 6 buttons; carousel/list collections max 10 cards; connector cards max 10 sections x 5 images x 5 actions. Teams' card reference itself is now marked "legacy", pointing to a new hub at adaptivecards.microsoft.com (adaptivecards.io now 301-redirects there). Best practice: no horizontal scroll, ColumnSets <= 3 columns, explicit widths ~48px max. Templating with `${...}` data binding. — [Teams cards reference (updated 2026-08-19)](https://learn.microsoft.com/en-us/microsoftteams/platform/task-modules-and-cards/cards/cards-reference)
- Design note: the same card JSON renders in different hosts (Teams, Outlook, Copilot, Bot Framework); the Teams doc shows host-specific deltas (e.g., `Action.Submit` not supported in incoming webhooks). — [Teams cards reference](https://learn.microsoft.com/en-us/microsoftteams/platform/task-modules-and-cards/cards/cards-reference)

**Discord message components (Components V2)**
- Component type IDs: 1 Action Row, 2 Button, 3 String Select, 4 Text Input, 5 User Select, 6 Role Select, 7 Mentionable Select, 8 Channel Select, 9 Section, 10 Text Display, 11 Thumbnail, 12 Media Gallery, 13 File, 14 Separator, 17 Container, 18 Label, 19 File Upload, 21 Radio Group, 22 Checkbox Group, 23 Checkbox. — [Discord components reference](https://docs.discord.com/developers/components/reference)
- Button styles: Primary/Secondary/Success/Danger (require `custom_id`, post an interaction back), Link (requires `url`), Premium (`sku_id`). `IS_COMPONENTS_V2` flag = `1 << 15`; once set it cannot be removed, disables `content`/`embeds`/polls/stickers; max 40 components per message; action row = 5 buttons or 1 select; Section = 1-3 Text Displays + one Button or Thumbnail accessory; `custom_id` 1-100 chars; button label 80, url 512 chars. — [Discord components reference](https://docs.discord.com/developers/components/reference)

**Google Chat Cards v2**
- Card = `header` (`title`, `subtitle`, `imageUrl`, `imageType` SQUARE/CIRCLE, `imageAltText`) + `sections[]` (optional `header`, `widgets[]`, `collapsible`, `uncollapsibleWidgetsCount`) + `fixedFooter`. Widgets (one of): textParagraph, image, decoratedText (top/bottom labels, icon, button/switch/checkbox), buttonList, textInput, selectionInput, dateTimePicker, divider, grid, columns (max 2), carousel, chipList. `onClick` is exactly one of `action` (calls an app `function` with `parameters`; `interaction: OPEN_DIALOG`), `openLink`, `openDynamicLinkAction` (add-on only), `card` (push a card, add-on only), `overflowMenu`. Max 100 widgets per card; excess sections silently dropped. — [Google Chat Card reference](https://developers.google.com/workspace/chat/api/reference/rest/v1/cards)

### Inferences
- The common action vocabulary across all four is: open URL/deep link, post-back with an opaque id + payload (Slack `action_id`/`value`, Discord `custom_id`, Adaptive `Action.Submit`/`Execute` `data`, Google `action.function` + `parameters`), open a host dialog/sub-view, toggle inline detail. Adeline needs only the first and third (open URI, open a mode's full view), plus maybe post-back to the mode.
- Slack Work Objects' split (public compact unfurl vs. detail pane fetched on demand via `entity_details_requested`) maps directly onto "card in transcript -> click -> full view in the mode's pane". The stable `external_ref` is the analogue of an Adeline entity id (file path, issue id).
- Every platform caps text lengths and child counts; this is how they keep transcript layout predictable on narrow widths. Adeline can encode the same caps in its card type.

### Gaps
- Exact introduction dates of Slack's Card/Carousel/Task card/Plan blocks and Work Objects were not stated on the fetched pages.
- The new Adaptive Cards hub (adaptivecards.microsoft.com) explorer returned 404 to the fetcher; the latest schema version beyond 1.6 could not be confirmed.
- Outlook Actionable Messages specifics not separately researched (covered only via Universal Action Model page).

## 2. AI-chat specific: MCP Apps, MCP-UI, OpenAI Apps SDK, Claude artifacts

### Takeaway
The AI-chat world standardized on **sandboxed HTML** rather than a declarative card vocabulary: MCP Apps (SEP-1865, stable spec 2026-01-26) renders a `ui://` HTML resource in a sandboxed iframe and talks to the host over JSON-RPC on postMessage. OpenAI's Apps SDK now sits on top of MCP Apps. MCP-UI's earlier non-iframe "remote-dom" option is not part of the current standard. None of this is cheap for a native GPUI host: it needs an embedded web engine.

### Cited Findings
- MCP Apps spec: SEP-1865, created 2025-11-21, status **Stable (2026-01-26)**, extension id `io.modelcontextprotocol/ui`. Only content type: `text/html;profile=mcp-app` (an `externalUrl` type is deferred). Tool `_meta.ui`: `resourceUri` (a `ui://` URI), `visibility` (`"model"` and/or `"app"`). Resource `_meta.ui`: `csp` (`connectDomains`, `resourceDomains`, `frameDomains`, `baseUriDomains`; restrictive default), `permissions` (camera, microphone, geolocation, clipboardWrite), `domain` (dedicated sandbox origin), `prefersBorder`. — [MCP Apps spec 2026-01-26](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx)
- MCP Apps methods. View->Host requests: `ui/initialize`, `ui/open-link`, `ui/message` (post into chat), `ui/request-display-mode`, `ui/update-model-context`; notifications `ui/notifications/initialized`, `ui/notifications/size-changed`. Host->View: `ui/notifications/tool-input`, `tool-input-partial`, `tool-result`, `tool-cancelled`, `host-context-changed`; request `ui/resource-teardown`. Views may also use `tools/call`, `resources/read`, `notifications/message`, `ping`. Display modes: `inline` (default), `fullscreen`, `pip`, declared in `appCapabilities.availableDisplayModes`. Theming: host sends `HostContext.theme` (light/dark) and `HostContext.styles.variables` (colors, fonts, sizes, radius, shadows) plus optional `styles.css.fonts`. Web hosts must use a double-iframe sandbox proxy on a separate origin. — [MCP Apps spec 2026-01-26](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx)
- Host flow: tool description carries `_meta.ui.resourceUri`; host can preload the resource before the call (enables streaming tool input into the app); renders in a sandboxed iframe; app can call server tools, send messages, update model context. Host may restrict which tools an app may call or disable open-link. Supported (per MCP site) by Claude, Claude Desktop, VS Code GitHub Copilot, Microsoft 365 Copilot, Goose, Postman, MCPJam, Archestra. Hosts can use `@mcp-ui/client` (React) or the SDK's AppBridge. — [MCP Apps overview](https://modelcontextprotocol.io/extensions/apps/overview)
- VS Code announced "full MCP Apps support" on 2026-01-26 (Insiders, Stable the following week); UI renders directly in the chat conversation. — [VS Code blog](https://code.visualstudio.com/blogs/2026/01/26/mcp-apps-support). A GitHub talk at AI Engineer Europe 2026 describes VS Code fetching the HTML resource and showing it in a sandboxed iframe. — [AI Engineer talk](https://ai.engineer/talks/building-interactive-uis-in-vs-code-with-mcp-apps-marlene-mhangami-liam-hampton-github)
- MCP-UI now describes itself as packages that "implement this standard" (MCP Apps); it pioneered UI over MCP and directly influenced the spec. Current docs only document `text/html;profile=mcp-app` resources rendered via `AppRenderer`/`AppFrame`; the earlier `text/uri-list` and `application/vnd.mcp-ui.remote-dom` types are not mentioned on the current intro page. — [MCP-UI intro](https://mcpui.dev/guide/introduction)
- OpenAI Apps SDK: widgets run in an iframe and use the MCP Apps bridge (JSON-RPC over postMessage); resource MIME `text/html;profile=mcp-app`; `_meta.ui.resourceUri` with `_meta["openai/outputTemplate"]` kept as a compatibility alias. `window.openai` adds only non-standard extras: `toolInput`, `toolOutput`, `widgetState`/`setWidgetState`, `callTool`, `sendFollowUpMessage`, `requestModal`, `requestCheckout`, `uploadFile`, `selectFiles`, `getFileDownloadUrl`; feature-detect, don't branch on host name. Display modes: inline card, inline carousel, fullscreen, picture-in-picture. Guidance: inline cards should be self-contained, no deep navigation. (Older `text/html+skybridge` MIME is no longer mentioned; treat as legacy.) — [OpenAI Apps SDK: ChatGPT UI](https://developers.openai.com/apps-sdk/build/chatgpt-ui)
- Claude artifacts: Simon Willison describes artifacts as running in a strictly controlled browser sandbox where localStorage and external fetch are restricted by CSP headers and the iframe sandbox. — [Simon Willison, 2026-04-03](https://simonwillison.net/2026/Apr/3/test-csp-iframe-escape/). Hosting on claudeusercontent.com with header CSP is reported only by a secondary source. — [agentpatterns.ai](https://www.agentpatterns.ai/security/browser-sandbox-agent-generated-html/). A claude.ai issue reported `_meta.ui.csp.frameDomains` being ignored by the host. — [claudeissues mirror](https://claudeissues.com/issue/59351-claude-ai-mcp-apps-host-silently-drops-meta-ui-csp-framedomains-blocking-all-thi)

### Inferences
- MCP Apps' action surface is small and worth copying even without HTML: open-link, post a message, update model context, call a tool, request a display mode (inline -> fullscreen). "Card click opens full view" is literally `ui/request-display-mode: fullscreen` in MCP Apps terms.
- For Adeline, supporting MCP Apps would mean embedding a webview (wry/WebView2/WKWebView) inside GPUI. That is a separate, heavier decision than built-in mode cards; mode cards for Docs/Issues should not depend on it.
- Inline-card guidance (OpenAI: no deep navigation; Slack: unfurl vs flexpane) consistently says the transcript card is a summary and the real interaction lives in a larger surface.

### Gaps
- No official Anthropic doc found describing artifact rendering internals.
- Whether ACP (Agent Client Protocol) has its own UI/card extension as of 2026 was outside this search; worth checking separately.
- MCP-UI remote-dom status (deprecated vs. still supported in `@mcp-ui/client`) not confirmed.

## 3. Native-host-rendered extension UI: Raycast, Zellij, VS Code, JetBrains, Obsidian, Warp

### Takeaway
Two families. (a) Closed vocabulary drawn by the host: Raycast (React -> JSON render tree -> AppKit), Zellij (WASM plugin emits serialized components that the host draws with its theme), VS Code chat response parts (markdown, anchors, buttons, file trees, references). (b) Raw toolkit access: Obsidian (DOM), JetBrains (Swing / Kotlin UI DSL), VS Code webviews. Warp has no public extension UI API.

### Cited Findings
- Raycast: extensions run outside the main app in a Raycast-managed Node runtime, one worker thread per extension (memory caps, crash isolation). A custom React reconciler turns each render into a JSON "render tree" sent over JSON-RPC on stdio; only registered messages (render, set-clipboard, ...) are accepted. Native side diffs trees with JSON Patch, gzips large trees, and drives custom AppKit components through Swift view models; the view-model layer insulates native UI from render-tree format changes. Goal stated as not "a second-class mini-app that shows in some frame". AppKit chosen over SwiftUI for crash rate/perf; Node chosen over JavaScriptCore for npm compatibility. Security relies on worker isolation, memory limits, mandatory store review and open-source extensions, not process sandboxing. — [Raycast blog: How the Raycast API and extensions work](https://www.raycast.com/blog/how-raycast-api-extensions-work)
- Raycast component set: List, Grid, Detail, Form, MenuBarExtra; `ActionPanel` with sections; built-in actions such as `Action.OpenInBrowser`, `Action.CopyToClipboard`, `Action.Paste`, `Action.Open`, and `Action.Push` (push a target view onto a navigation stack, `useNavigation` push/pop). Built-in actions keep extensions aligned with Raycast's interface guidelines. — [Raycast Actions API](https://developers.raycast.com/api-reference/user-interface/actions); [@raycast/api type definitions](https://cdn.jsdelivr.net/npm/@raycast/api@1.104.9/types/index.d.ts)
- Zellij: plugins are WASM (wasm32-wasip1) modules whose `render(rows, cols)` prints to stdout; plain ANSI is allowed. Built-in UI components Table, Ribbon, Nested List, Text are serialized by SDK wrappers into a private terminal DCS extension the host interprets (element name, coordinates, selected/opaque flags, colored index ranges). Host-drawn components pick up the user's theme (index colors, selection, success/error colors). — [Zellij plugin UI rendering](https://zellij.dev/documentation/plugin-ui-rendering.html); [Zellij new plugin system](https://zellij.dev/news/new-plugin-system/)
- VS Code chat participants: `ChatResponseStream` parts are `markdown()` (images/links only from trusted domains), fenced code blocks (with apply-to-editor controls), command links (`command:` URIs in a `MarkdownString` with `isTrusted` listing allowed command ids), `button()` (command id + title), `filetree()` (file tree with preview), `progress()`, `reference()` (file, `Location`, or URL into a references list), `anchor()` (inline reference to a URI, location or symbol). Followups via `ChatFollowupProvider` returning `{prompt, label}`. The chat guide does not mention webviews in chat. — [VS Code Chat Participant API](https://code.visualstudio.com/api/extension-guides/ai/chat)
- JetBrains: Kotlin UI DSL v2 (`com.intellij.ui.dsl.builder`, `panel { row("...") { textField() } }`) is for forms/dialogs/settings; tool windows use IntelliJ Platform or standard Swing components; Swing work must run on the EDT. Plugins therefore get the real toolkit, not a vocabulary. — [Kotlin UI DSL v2](https://plugins.jetbrains.com/docs/intellij/kotlin-ui-dsl-version-2.html)
- Obsidian: plugins extend `ItemView`/`FileView`, register with `registerView(type, leaf => new View(leaf))`, and build content directly into the view's container element in `onOpen()` (i.e., raw DOM). Sources were third-party mirrors of the API docs. — [obsidian-api mirror: creating views](https://mintlify.com/obsidianmd/obsidian-api/guides/creating-views)
- Warp: no official public extension/plugin UI API found; a long-standing GitHub discussion requests one. Third-party CLI agents integrate via a Warp-defined OSC 777 notification protocol (escape sequences), not an SDK. — [Warp discussion #435](https://github.com/warpdotdev/Warp/discussions/435); [Warp integrations docs](https://docs.warp.dev/integrations-and-plugins); [pi-warp README](https://cdn.jsdelivr.net/gh/capyup/pi-warp@main/README.md)

### Inferences
- VS Code's `anchor`/`reference`/`filetree`/`button` parts are the closest precedent for "a card for a newly created .md file": a typed reference to a URI, rendered by the host with its own icons, opening the host's own editor on click. No extension-supplied drawing code.
- Raycast and Zellij show the pattern works for a native or terminal host: the extension emits data (a tree of known node types), the host owns layout, theming, keyboard handling and accessibility. Raycast's JSON-Patch diffing is only needed when extension code is out of process and re-renders often; Adeline's built-in modes run in-process.
- Warp's choice of escape-sequence notifications is a reminder that agent-facing protocols can carry structured UI hints over existing channels (for Adeline, ACP message metadata).

### Gaps
- VS Code webview/custom editor/notebook renderer details were not re-fetched in this session (known model: webviews are iframes with postMessage and CSP; notebook renderers are JS modules run in the notebook webview). Check https://code.visualstudio.com/api/extension-guides/webview before citing specifics.
- Did not confirm whether VS Code chat now exposes `ChatResponseReferencePart` variants like confirmation/warning parts (proposed APIs) as of 2026.
- No primary Raycast doc page listing the full component reference was fetched; list above comes from Raycast actions page and type definitions.

## 4. Pros/cons, and which pattern fits a native GPUI app

### Takeaway
For built-in modes in a native GPUI app, a small typed card enum (data + action, rendered by the host) wins on theming, accessibility, keyboard navigation, performance and security; webviews only make sense later for third-party MCP Apps; raw code access (Obsidian/JetBrains style) is only viable when plugins are trusted and in-process, which conflicts with Adeline's engine/client split.

### Cited Findings
- Fixed vocabulary keeps host consistency: Raycast built-in actions keep extensions aligned with its interface guidelines — [Raycast Actions](https://developers.raycast.com/api-reference/user-interface/actions); Zellij host-drawn components inherit theme colors — [Zellij UI rendering](https://zellij.dev/documentation/plugin-ui-rendering.html); Adaptive Cards rely on host rendering so the same JSON works across Teams/Outlook/Copilot, at the cost of per-host feature deltas (Teams max v1.6, no positive/destructive styling) — [Teams cards reference](https://learn.microsoft.com/en-us/microsoftteams/platform/task-modules-and-cards/cards/cards-reference).
- Fixed vocabulary costs expressiveness and forces hard limits (Slack card: 3 buttons, 150/200-char fields; Discord: 40 components; Google: 100 widgets) — sources in section 1.
- Webviews give full expressiveness but need a sandbox, CSP, a message bridge, and host-pushed theme variables to look native (MCP Apps `HostContext.styles.variables`, double-iframe proxy) — [MCP Apps spec](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx). Raycast explicitly rejected the "mini-app in a frame" feel — [Raycast blog](https://www.raycast.com/blog/how-raycast-api-extensions-work).
- Security of declarative cards still needs care: Slack warns that unfurling links in LLM-generated messages can exfiltrate data via prompt injection — [Slack unfurling](https://docs.slack.dev/messaging/unfurling-links-in-messages); VS Code requires explicit `isTrusted` command allowlists for command links and only renders images/links from trusted domains — [VS Code chat](https://code.visualstudio.com/api/extension-guides/ai/chat).
- Slack Work Objects separate a public summary card from an on-demand detail pane fetched by event — [Slack Work Objects](https://docs.slack.dev/messaging/work-objects-overview).

### Inferences
- Recommended shape for Adeline (inference, not sourced): the engine emits, per transcript item, a typed `Card { kind, entity_ref, title, subtitle, body/excerpt, icon, badges/facts[], actions[] }` where `entity_ref` is stable (file path, issue id; like Slack `external_ref`) and `actions` come from a closed enum (`OpenEntity` -> mode's full view, `OpenUri`/reveal, `Copy`, maybe `Invoke { mode, action_id, payload }` post-back like Discord `custom_id`). The UI renders each `kind` with GPUI components, owns focus/keyboard shortcuts and theme. Clicking `OpenEntity` asks the owning mode to show its full view (Slack flexpane / MCP Apps fullscreen analogue); detail data is fetched on open, not stuffed into the card.
- Where cards come from: either explicit (mode emits a card when its tool creates a .md / an issue) or by unfurling (UI recognizes a path/URL in agent output and asks the owning mode for a card, like `link_shared` -> `chat.unfurl`). Unfurling covers agent-created artifacts without agents knowing about cards; explicit emission is simpler and deterministic. Start with explicit; add path/URL recognition if agents produce links the mode did not create.
- Because cards cross the engine-client boundary, the card enum is part of the wire protocol; its shape changes need protocol versioning (Adaptive Cards `version`, Discord flags show the cost of retrofitting).
- Keep length caps and a max action count in the type (Slack's 3-button card is a good default) so the transcript stays scannable.
- Defer MCP Apps/webviews until third-party UI is actually needed; if added, render them only in the full-view pane, not inline, to limit cost and keep the transcript native.

### Gaps
- No public write-up found of a GPUI (Zed) extension UI precedent; Zed's own extension model (WASM, no UI contributions beyond limited surfaces) was not researched here and is worth a separate check.
- No measured performance comparison (native vs. webview card rendering) was found.

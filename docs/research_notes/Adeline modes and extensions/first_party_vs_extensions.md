# First-party features ("modes") vs third-party extensions, and cross-feature contribution

Research date: 2026-10-14. Scope: how multi-feature apps split built-in features from extensions, and how one feature puts cards, renderers or links into another feature's view. Context: deciding whether Adeline's built-in modes (Docs, Issues, Workflows, Whiteboard, Group chats) should use a public extension API or be deeper built-in modules. Adeline is a Rust GPUI app, so Zed is the closest analogue.

## 1. VS Code: what built-ins use the public API, and what is core-only?

### Takeaway
VS Code has two tiers. "Workbench contributions" (`src/vs/workbench/contrib`: search, git UI, debug, chat) are built into core and use an internal mechanism, not the extension API. "Built-in extensions" (`extensions/`: git, markdown, emmet, TypeScript) run in the extension host and use the public API, plus proposed APIs that only first-party or allow-listed extensions may ship. So VS Code dogfoods its public API for language and tool integrations, but keeps UI shell features and new surfaces (chat, notebooks at first) in core.

### Cited Findings
- Core layers are `base` / `platform` / `editor` / `workbench` / `code` / `server`. Workbench features such as search, git and debug live in `vs/workbench/contrib`. "Contributions that are contributed to the workbench all live inside the `vs/workbench/contrib` folder." Rules: nothing outside `contrib` may depend on it; each contribution has one `.contribution.ts` entry and exposes its internal API through one common file; a contribution may use another contribution's common API but never its internals. — [VS Code wiki: Source Code Organization](https://github.com/microsoft/vscode/wiki/Source-Code-Organization)
- The wiki says contrib uses "an internal (as opposed to real extension API) mechanism". Built-in extensions live under `extensions/` and run in a separate extension host process. — [VS Code wiki: Source Code Organization](https://github.com/microsoft/vscode/wiki/Source-Code-Organization)
- Proposed APIs are implemented but unstable, "only available in Insiders distribution", enabled per extension via `enabledApiProposals`, and "should not be used in published extensions" on the Marketplace. In practice this is a privileged lane for first-party extensions (Copilot and built-ins ship in-product with proposals enabled). — [Using Proposed API](https://code.visualstudio.com/api/advanced-topics/using-proposed-api)
- Extensions get no DOM access and no custom stylesheets. VS Code wants "the freedom to make changes to the user interface", and the DOM and class names are internal. Extension UI goes through fixed surfaces: TreeViews, Activity Bar views, Status Bar, Webviews, SCM providers, menus. — [Extension Capabilities Overview](https://code.visualstudio.com/api/extension-capabilities/overview)
- Isolation rationale: "extensions can also affect startup performance or the overall stability of VS Code itself. To avoid these problems, VS Code loads and runs extensions in a separate process, the extension host process. A misbehaving extension cannot impact VS Code and in particular its startup time." Activation is lazy, so unused extensions use no memory. — [Our Approach to Extensibility (archived docs mirror)](https://vscode-docs1.readthedocs.io/en/stable/extensions/our-approach/) (older doc, but the principle still holds)
- 2026: VS Code moved long-running agent session orchestration out of the extension host into a dedicated "agent host" process. A third-party comparison lists "blocked by a busy extension" as a weakness of the extension-host model. — [ecorpit: VS Code 1.129 agent host](https://ecorpit.com/vscode-1-129-agent-host-platform-team-rollout-2026/) (secondary source)

### Cross-feature mechanisms in VS Code (public API)
- **Custom editors / "Reopen With"**: `contributes.customEditors` with `viewType`, `selector` (`filenamePattern` globs like `*.png` or `**/translations/*.json`), and `priority` `"default"` (used automatically) or `"option"` (shown in "Reopen with", can be made the user default). Activation is lazy via `onCustomEditor:VIEW_TYPE`. — [Custom Editor API](https://code.visualstudio.com/api/extension-guides/custom-editors)
- **Opener resolution**: `vscode.commands.executeCommand('vscode.open', uri)` goes through the editor resolver and respects `workbench.editorAssociations` and custom editor registrations. `showTextDocument()` forces the text editor. — [Claude Code issue citing VS Code behaviour](https://claudeissues.com/issue/38684-bug-claude-code-vs-code-extension-opens-files-with-showtextdocument-bypassing-cu) (secondary)
- **URI handler / deep links**: `window.registerUriHandler` receives `vscode://publisher.extension/...`. Use `env.uriScheme` (Insiders is `vscode-insiders://`) and `env.asExternalUri` for remote/web. VS Code does not let external processes call arbitrary commands, so deep links reach only handlers the extension defines. — [Elio Struyf: callback to your extension](https://www.eliostruyf.com/callback-extension-vscode); [Claude Code deep-link issue](https://claudeissues.com/issue/10366-add-deep-linking-support-to-open-specific-chats-e-g-vscode-anthropic-claude-code)
- **DocumentLinkProvider**: turns ranges in a document into clickable links with a target URI and tooltip. Links can be resolved lazily with `resolveDocumentLink`. The editor ships a default http(s)/file link provider. — [vscode-api DocumentLinkProvider](https://vscode-api.js.org/interfaces/vscode.DocumentLinkProvider.html)
- **One built-in extending another (closest analogue to "Docs contributes into Chat")**: the built-in Markdown preview has its own contribution points: `markdown.previewStyles` (CSS loaded after built-in styles), `markdown.markdownItPlugins` + `extendMarkdownIt(md)` (syntax; contributors are "activated lazily, when a Markdown preview is shown for the first time"), and `markdown.previewScripts` (JS in the preview, used by Mermaid support). So a feature defines its own extension points and other features plug into them. — [Markdown Extension guide](https://code.visualstudio.com/api/extension-guides/markdown-extension)
- **Chat participants and response parts**: `contributes.chatParticipants` + `vscode.chat.createChatParticipant`. `ChatResponseStream` offers typed parts: `markdown`, command links (`command:` URIs, need `isTrusted`), `button`, `filetree` ("lets users preview individual files"), `progress`, `reference` (file/selection/URL in a references list), `anchor` (inline link to URI or symbol). Images/links only from trusted domains. — [Chat Participant API](https://code.visualstudio.com/api/extension-guides/ai/chat)
- Chat output renderers: VS Code core has a `chatOutputRendererService` that registers renderers per view type and renders tool output into a webview. It is only seen in an unofficial source mirror. — [unofficial mirror](https://v48tuyih0eytvyiwyd84kwv0.core.boriel.com/02f35f4a-3f95-45d7-8cfb-16ced3baa8aa?page=8) (unverified; see Gaps)

### Inferences
- VS Code's split falls along "shell/UI framework and new fast-moving surfaces = core contrib" versus "integrations that fit stable surfaces = extensions on public API". Proposed APIs let first-party extensions move faster without freezing the API.
- Even inside core, contrib modules talk only through a published "common" API file. That is a light internal contract, not the full public API, and it suits Adeline modes as crates.
- For "a .md in chat opens Docs": in VS Code terms, chat emits a typed `reference`/`anchor` part holding a URI, and opening it goes through `vscode.open`'s resolver, which picks the editor registered for that file pattern. The chat does not know about the Markdown feature.

### Gaps
- No official doc confirms the exact status of a public or proposed `chatOutputRenderer` API in 2026. Check `src/vscode-dts/vscode.proposed.chatOutputRenderer.d.ts` in the repo.
- I did not verify whether built-in image preview / markdown preview are registered via `customEditors` (I believe image preview is, as a built-in extension, but that is unconfirmed here).

## 2. Zed: built-in crates vs restricted WASM extensions

### Takeaway
Zed's built-in features (assistant/agent panel, terminal, git, collab channel notes) are Rust crates with an `init(cx)` that hooks into `Workspace` and implements `Panel`/`Item` traits. Extensions are WASM components behind a WIT interface. As of the latest docs they can only add languages, themes, icon themes, snippets, MCP servers, debuggers, and (via the ACP registry) agent servers. They cannot add UI panels. Zed's own explanation is priority and maturity ("there's a ton to do"), not a stated principle.

### Cited Findings
- Extensions were written in Rust, compiled to WASM, and use the WebAssembly Component Model. When that matured "everything just sort of clicked together". There is "no support for modifying the UI to create new panels", no arbitrary HTTP, and no unrestricted filesystem access. The limits are attributed to the team not having reached a more powerful API yet. Post dated 2024-10-21. — [Zed Decoded: Extensions](https://zed.dev/blog/zed-decoded-extensions) (older, but the restriction still holds per docs below)
- Current docs list extension capabilities: languages, themes, icon themes, snippets, MCP servers, debuggers. No UI or panels. — [Zed docs: Extensions](https://zed.dev/docs/extensions)
- Built-in panel pattern (assistant panel, v0.181): `init(cx)` uses `cx.observe_new` on `Workspace` to `register_action` for each new workspace, and calls `FollowableViewRegistry::register`. Panels implement the dock `Panel` trait and hold `WeakEntity<Workspace>`. Tabbed content goes through a `Pane` of `Item`s. — [assistant_panel.rs mirror](https://git.secluded.site/zed/blob/v0.181.3-pre/crates/assistant/src/assistant_panel.rs); [Introduce tabs to assistant panel](https://git.secluded.site/zed/commit/818e6e53d625378a00ae3418a3991cdd2c78d249)
- Zed architecture: `Entity<Workspace>` holds panes and panels, `Entity<Project>` holds LSP/Git/DAP services, so UI and services stay separate. — [Mintlify Zed architecture](https://www.mintlify.com/zed-industries/zed/contributing/architecture); [DeepWiki Zed overview](https://deepwiki.com/zed-industries/zed/1-overview) (both generated docs, secondary)
- Deep links: `open_listener` parses `zed://` URLs into typed variants (`Channel`, `ChannelNotes`, `zed://ssh`, `zed://settings`) and dispatches each to a handler. A late-2025 fix made in-editor clicks on channel/channel-note links open directly instead of bouncing through the web. `cli: Register Zed Scheme` picks which install handles `zed://`. — [Fix link opening #44910](https://git.secluded.site/zed/commit/829b1b5661dbcf976489c3d8021acdb8f4ed6af9); [Remove release channel from Zed URLs #8863](https://git.secluded.site/zed/commit/f53823c840cdb80c65e9c7fc5dd7a416d72d3ead); [Zed CLI docs](https://git.secluded.site/zed/blob/main/docs/src/reference/cli.md?source=1)
- Atom lesson as applied to Zed: a third-party blog argues that Atom's extension boom brought incompatible APIs and a codebase trapped by backward compatibility, and that Zed's answer is bounded plugins. This is the blog author's interpretation; no direct Sobo quote was found. — [Peerlist: Zed fighting for milliseconds](https://peerlist.io/vi_c0de/articles/zed-editor-fighting-for-milliseconds)

### Inferences
- Zed is the clearest example of "first-party features as deep built-in modules, extensions as narrow typed slots". In-process Rust with GPUI entities can't be safely exposed across a WASM boundary without a big stable view API, which Zed has not built.
- Zed routes in-app links through one parser (`open_listener`) that maps URL kinds to handlers in different crates. That is a central opener registry keyed by URL shape, which fits Adeline's "chat link opens Docs" case.

### Gaps
- No official Zed statement of the long-term policy (whether UI extensions are planned for 2026). No public 2026 roadmap found.
- Exact current `Panel`/`Item` trait signatures not fetched; read `crates/workspace/src/dock.rs` and `item.rs`.

## 3. Other apps: Obsidian, JetBrains, Eclipse, Raycast, Warp, Slack, Notion, Linear

### Takeaway
Apps that put core features on the same plugin model (JetBrains, Eclipse, Obsidian, Raycast in part) still keep an "internal" tier: `@ApiStatus.Internal`, core-plugin-only hooks, private APIs. Cross-app link enrichment (Slack, Notion) is always a registry keyed by URL domain or pattern, plus a typed card payload that the host renders.

### Cited Findings
- **Obsidian**: the public `Plugin` API offers `registerView(type, creator)`, `registerExtensions(exts, viewType)` (file extension → view), `registerObsidianProtocolHandler(action, handler)` (`obsidian://action`), `registerMarkdownPostProcessor` (transform rendered reading view), `registerMarkdownCodeBlockProcessor(lang, …)` (render a fenced block into a div), `registerEditorExtension` (CM6), `registerHoverLinkSource` (makes a view emit hover-link events for the **Page preview core plugin**), `registerBasesView`, `registerCliHandler`. — [Obsidian Plugin reference](https://docs.obsidian.md/Reference/TypeScript+API/Plugin)
- `registerHoverLinkSource` is a public hook whose consumer is a core plugin, so community plugins feed into a core feature's view. — [Obsidian Plugin reference](https://docs.obsidian.md/Reference/TypeScript+API/Plugin)
- Markdown post-processors also fire for `MarkdownRenderer.render` calls and preview popups, not just the open note. Developers asked for the associated View in the context because the processor can't tell where it is rendering. — [Obsidian forum](https://forum.obsidian.md/t/expose-associated-view-in-markdownpostprocessor/106092); [Markdown post processing docs](https://docs.obsidian.md/Plugins/Editor/Markdown+post+processing)
- Core and community plugins are stored in separate configs (`core-plugins.json` vs `community-plugins.json`). No public source found saying core plugins use only the public API. — (search summary; see Gaps)
- **JetBrains**: more than 1600 extension points across the platform and bundled plugins. `@ApiStatus.Internal` is "private API and must not be used outside of IntelliJ Platform itself". Plugin Verifier and an IDE inspection flag violations. Bundled plugins can declare internal-only extension points (e.g. GoLand `com.goide.consoleDecorator`). — [Plugin extensions](https://plugins.jetbrains.com/docs/intellij/plugin-extensions.html); [Internal API](https://plugins.jetbrains.com/docs/intellij/api-internal.html); [Verifying compatibility](https://plugins.jetbrains.com/docs/intellij/verifying-plugin-compatibility.html); [GoLand EP list](https://plugins.jetbrains.com/docs/intellij/goland-extension-point-list.html)
- **Eclipse**: microkernel plus plug-in architecture with "controlled extensibility". Eclipse 3.0 moved to an OSGi runtime "to support dynamic plug-ins and to provide more configurability". — [ACM: Erich Gamma](https://awards.acm.org/award-recipients/gamma_2579548); [JKU talk abstract](https://informatik.jku.at/kolloquium/listTalk.jsp?talkId=107) (2004-era)
- **Raycast**: extensions run in a managed Node runtime (worker threads). React output goes through a reconciler as a JSON render tree with JSON Patch diffs, and is rendered with native AppKit components. "The Node process can crash without crashing Raycast itself." Raycast **ported formerly built-in Swift features (GitHub, Linear, Google Workspace, Zoom) to open-source API extensions**, and "Those extensions have become the baseline and informed what we need to build and expose through the API." Post 2023-05-31. — [Raycast: How the API and extensions work](https://raycast.com/blog/how-raycast-api-extensions-work)
- Raycast ships built-in extensions alongside thousands of Store ones. The source does not say all built-ins use `@raycast/api`. — [Raycast manual: Extensions](https://manual.raycast.com/extensions.md)
- **Warp**: Drive objects (workflows, notebooks, prompts) are shared via `https://www.warp.dev/drive/...` links that open in the desktop app by default (a setting). The `warp://` scheme only covers `action/new_window`, `action/new_tab`, `launch/<config>`. Notebook permalinks were announced as planned in 2024. — [Warp URI scheme](https://docs.warp.dev/features/uri-scheme); [Warp Drive on the web](https://docs.warp.dev/knowledge-and-collaboration/warp-drive/warp-drive-on-the-web); [Notebooks in Warp Drive](https://www.warp.dev/blog/notebooks-in-warp-drive)
- **Slack unfurls**: apps register up to five "App unfurl domains", subscribe to `link_shared` (gets channel, ts and matching links but not message text), and reply with `chat.unfurl`, an `unfurls` map keyed by URL to Block Kit blocks or a `preview`. Composer-time unfurls use `unfurl_id` + `source=composer`. Only the first installed app for a domain gets the event. No events for app-posted messages. Slack advises disabling unfurls on LLM-generated messages to reduce data-exfiltration risk. **Work Objects** add richer, real-time entity previews (files, tasks, tickets). — [Slack: Unfurling links in messages](https://docs.slack.dev/messaging/unfurling-links-in-messages/)
- **Notion Link Previews API**: integrations show authenticated live content for pasted links from their domain. It needs access approval, domain ownership verification, and OAuth (public integration). Notion's internal archive says custom Link Preview connections are "no longer available for new developers", which conflicts with the public build guide. — [Notion Link Previews API](https://developers.notion.com/page/link-previews-api); [Build a link preview integration](https://developers.notion.com/docs/build-a-link-preview-integration); [Notion internal archive](https://developers.notion.com/guides/internal/link-previews/building-a-link-preview)
- **Linear in Slack**: no primary source found in this pass (see Gaps).

### Inferences
- Every unfurl system is the same pattern: (1) the owner registers a match key (domain, URL pattern, file glob, URI scheme); (2) the host detects a match in content it owns; (3) the owner returns a typed, host-rendered card (Block Kit, Work Object, Notion preview) rather than arbitrary UI; (4) clicking deep-links back to the owner. Adeline's "Docs registers `*.md` → card in chat; click opens Docs with chat in a sidebar" fits this directly.
- Raycast is the one strong counter-example where moving built-ins onto the public API paid off: it shaped the API. It worked because Raycast's UI is a small set of declarative components (List/Detail/Form), and a whiteboard or doc editor would not fit that.

### Gaps
- Linear's Slack unfurl and Linear's own integration directory docs were not fetched.
- Emacs, Neovim and Figma not researched in this pass. From background knowledge, unverified: Emacs and Neovim ship most "features" as Lisp/Lua in the same runtime as user packages (full dogfooding, no isolation). Figma plugins run in a sandboxed JS realm with an iframe for UI and cannot extend Figma's own panels.
- No source confirms whether Obsidian core plugins are written against the public API only.

## 4. Downsides of dogfooding vs not; known essays

### Takeaway
No canonical postmortem says "dogfood" or "don't". The evidence is indirect. VS Code isolates extensions and hides the DOM to keep UI freedom and startup performance, and keeps shell features in internal contrib. Atom (everything a package, in-process, full DOM access) was sunset, and its successor Zed went the other way. JetBrains and Eclipse dogfood the plugin model but need an internal-API tier and tooling to stop third parties depending on it.

### Cited Findings
- VS Code's reason for not exposing UI internals: DOM and class names are undocumented so the team keeps "the freedom to make changes to the user interface". — [Extension Capabilities Overview](https://code.visualstudio.com/api/extension-capabilities/overview)
- VS Code's reason for process isolation: stability and startup, "A misbehaving extension cannot impact VS Code". — [Our Approach to Extensibility](https://vscode-docs1.readthedocs.io/en/stable/extensions/our-approach/)
- Proposed APIs as a velocity escape hatch: unstable, Insiders-only, not for Marketplace, so first-party code can use new surfaces before they are frozen. — [Using Proposed API](https://code.visualstudio.com/api/advanced-topics/using-proposed-api)
- Atom sunset (announced June 2022): GitHub cited no significant feature development for years and declining community involvement, and a focus on Codespaces. No formal technical postmortem of the package architecture exists. Example of ecosystem fragility: an unresolved bug blocked installing plugins. — [TechCrunch](https://techcrunch.com/2022/06/08/github-sunsets-atom-the-software-dev-environment-it-launched-in-2011); [WakaTime: The End of Atom](https://wakatime.com/blog/53-the-end-of-atom)
- Atom's founder went on to build Zed (Rust, native, restricted WASM extensions). — [The Changelog #531 / Goodbye Atom, hello Zed](https://changelog.com/podcast/531)
- JetBrains needs `@ApiStatus.Internal`, Plugin Verifier and migration guides because one shared model leaks internals to third parties. Internal status of APIs also changes over time. — [Internal API](https://plugins.jetbrains.com/docs/intellij/api-internal.html)
- Raycast: dogfooding built-ins as extensions defined the API baseline. — [Raycast blog](https://raycast.com/blog/how-raycast-api-extensions-work)

### Inferences
- **Costs of dogfooding a public API for core features**: every internal need becomes public surface, which then freezes (VS Code avoids this with proposed APIs, JetBrains with `@Internal`). The serialization or process boundary costs latency and rich-UI ability (no DOM in VS Code, no panels in Zed, declarative components only in Raycast). And core velocity is tied to API design.
- **Costs of not dogfooding**: extensions get second-class surfaces (Zed has no panels, VS Code has webviews instead of native views), and the API is under-tested because nobody internal uses it.
- **Common middle path** (VS Code contrib, Zed crates, JetBrains bundled plugins with internal EPs): build first-party features as separate modules with a strict internal contract (one entry point, one public "common" API, no reaching into internals, registries instead of direct calls). Expose a narrower, stable, typed subset publicly, and move pieces from internal to public once they have settled.
- For Adeline specifically (Rust/GPUI, no extension runtime yet): the Zed pattern (crate per mode, `init(cx)`, registries) costs least now. Defining cross-mode contracts as registries (opener-by-URI, renderer-by-content-type) means a later WASM/ACP extension API can expose the same registries without rewriting the modes.

### Gaps
- No primary-source "Eclipse lesson" essay found. The link between Gamma's Eclipse experience and VS Code's isolation is commonly claimed but not documented in what I found.
- No Nathan Sobo primary quote on Atom's API surface found.

## 5. Cross-feature integration patterns (registries, deep links, events, typed references)

### Takeaway
Across these apps the same few mechanisms keep showing up. (a) An **opener/resolver registry** keyed by URI scheme or file glob, with priority and user override. (b) **Content renderers** keyed by content type, language or file pattern, which the host view calls for content it owns. (c) **Typed reference parts** in messages (URI plus kind) instead of raw text. (d) **Deep-link URLs** routed through one parser to per-feature handlers. (e) **Feature-owned extension points**, where a feature like the Markdown preview exposes its own hooks.

### Cited Findings
- Opener by file pattern with priority `default`/`option` and user association: VS Code `customEditors` + `vscode.open` resolver + `workbench.editorAssociations`. — [Custom Editor API](https://code.visualstudio.com/api/extension-guides/custom-editors); [issue noting resolver behaviour](https://claudeissues.com/issue/38684-bug-claude-code-vs-code-extension-opens-files-with-showtextdocument-bypassing-cu)
- File extension → view type: Obsidian `registerExtensions(exts, viewType)` + `registerView`. — [Obsidian Plugin reference](https://docs.obsidian.md/Reference/TypeScript+API/Plugin)
- Renderer by content kind inside another feature's view: Obsidian `registerMarkdownCodeBlockProcessor(language, …)` and post-processors; VS Code `markdown.markdownItPlugins` / `previewScripts`. — [Obsidian](https://docs.obsidian.md/Reference/TypeScript+API/Plugin); [VS Code Markdown extension](https://code.visualstudio.com/api/extension-guides/markdown-extension)
- Typed reference parts in chat: VS Code `stream.reference`, `stream.anchor`, `stream.filetree`, `stream.button`. — [Chat Participant API](https://code.visualstudio.com/api/extension-guides/ai/chat)
- URL-pattern unfurl registries: Slack `app_unfurl_domains` + `link_shared` + `chat.unfurl`, Work Objects; Notion Link Previews (domain-verified). — [Slack](https://docs.slack.dev/messaging/unfurling-links-in-messages/); [Notion](https://developers.notion.com/page/link-previews-api)
- Deep-link routing: Zed `open_listener` parses `zed://channel/...`, `zed://ssh/...`, `zed://settings` into typed variants. VS Code `registerUriHandler` per extension. Obsidian `registerObsidianProtocolHandler(action)`. Warp `warp://action/...`. — [Zed #44910](https://git.secluded.site/zed/commit/829b1b5661dbcf976489c3d8021acdb8f4ed6af9); [Elio Struyf](https://www.eliostruyf.com/callback-extension-vscode); [Obsidian](https://docs.obsidian.md/Reference/TypeScript+API/Plugin); [Warp URI scheme](https://docs.warp.dev/features/uri-scheme)
- Events between features: Obsidian `registerHoverLinkSource` lets any view emit "hover-link" events that the Page preview core plugin consumes. — [Obsidian](https://docs.obsidian.md/Reference/TypeScript+API/Plugin)
- Security note for agent-generated content: Slack advises disabling unfurls on LLM-generated messages (exfiltration risk). VS Code only shows images/links in chat from trusted domains and needs `isTrusted` for command links. VS Code does not let external URIs run arbitrary commands. — [Slack](https://docs.slack.dev/messaging/unfurling-links-in-messages/); [VS Code chat](https://code.visualstudio.com/api/extension-guides/ai/chat); [deep-link issue](https://claudeissues.com/issue/10366-add-deep-linking-support-to-open-specific-chats-e-g-vscode-anthropic-claude-code)

### Inferences
- A minimal Adeline design that matches industry practice: chat messages carry typed resource references (path/URI + kind). The Docs mode registers at `init` (a) a card renderer for `*.md` references and (b) an opener for `adeline://docs/<path>?chat=<id>`. Chat looks up renderers by kind and falls back to a plain link, so it never imports Docs. Clicking dispatches the URI through one central opener, like Zed's `open_listener`, which activates Docs with the chat in a sidebar. The same URI works as an external deep link.
- Treat agent-produced links as untrusted. Only resolve local/workspace URIs automatically, and don't run actions from links (as in the VS Code and Slack guidance).

### Gaps
- No source found describing an "event bus" as the main cross-feature mechanism in any of these apps. Registries plus commands/actions are the norm (Zed actions, VS Code commands). Event buses show up only in narrow cases (Obsidian hover-link).

# Wrap the whole agent, not its commands

Adeline should support MXC by wrapping each ACP agent process in an MXC ProcessContainer from one spot, `Worker::start` in `crates/adeline_engine/src/acp/session.rs`. The model to copy is OpenAI Codex's `mxc-sandbox` crate: Adeline re-invokes its own executable as a small sandbox helper, so stdio pipes pass straight through. Adeline is a good fit for this. The engine runs no tools, edits no files and offers no ACP `fs/*` or `terminal/*` capability, so a boundary around the agent process covers every shell command, file edit and stdio MCP server the agent starts. That is stronger than Claude Code's own sandbox, which covers only shell commands and does not run on native Windows at all ([Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing)). MXC reached **GA on Windows 11 on 2026-10-07 with SDK v1.0.0** ([The Stack](https://www.thestack.technology/microsoft-takes-mxc-its-agent-management-layer-ga/)). The same SDK also drives Seatbelt on macOS and bubblewrap on Linux ([microsoft/mxc](https://github.com/microsoft/mxc)), so one Rust dependency can cover all of Adeline's engine hosts. The toggle should be layered, and every layer should resolve on the engine host. The global default goes in `EngineSettings`, a three-state override (inherit, on, off) goes in `AgentDefinition`, and the resolved value is frozen into the conversation's `ExecutionConfig` when the chat is created. Once the user asks for the sandbox, Adeline must never fall back to running unsandboxed. A Windows MVP with the global and per-agent toggles is about **1.5 to 2.5 weeks** of work. macOS, a per-conversation override, and a domain-allowlist proxy each add about one more week.

## Every Adeline agent launch already funnels through one function

The codebase makes this unusually cheap. Conversations, probes and logins all reach the OS through one chain: `acp::Driver::spawn` (`crates/adeline_engine/src/acp.rs:233-251`), then `Worker::start` (`session.rs:6-88`), then `adeline_core::platform::spawn_piped` (`crates/adeline_core/src/platform.rs:373-421`). On Windows, `spawn_piped` wires stdout and stderr through owner-only overlapped named pipes, and the engine has already put itself in a kill-on-close job object (`platform.rs:29-62`). `ExecutionConfig` (`crates/adeline_core/src/agents.rs:469-490`) is built in exactly two places. One is conversation creation (`crates/adeline_engine/src/storage.rs:637-663`). The other is `Engine::standalone`, used for probes and logins (`crates/adeline_engine/src/engine/projects.rs:118-152`). If you add a sandbox field there and branch in `Worker::start`, every agent launch becomes sandbox-aware.

The agent's real footprint comes from outside the repo, and it sets the policy. A sandboxed Claude Code or Codex needs these grants:

- read-write on the project directory
- read and execute on its npm global prefix and Node.js. Windows agents resolve to `.cmd` shims (`crates/adeline_core/src/install.rs:100-103`).
- read-write on its own state and credential directories
- `%TEMP%`, for attachment copies and probe directories (`crates/adeline_engine/src/acp/turns.rs:55-85`, `acp/probe.rs:13-15`)
- network egress to the model API

To wrap the whole Claude Code process, Anthropic's own guidance says to grant writes to `~/.claude`, `~/.claude.json` and its temp directory, and to allow `api.anthropic.com`, `claude.ai` and `platform.claude.com` ([Claude Code sandbox environments](https://code.claude.com/docs/en/sandbox-environments)). Adeline stores no credentials itself. The child inherits the engine's whole environment, and the codebase has no `env_clear` anywhere (`session.rs:38`). So the sandbox policy has to pass the environment explicitly, and that is the moment to decide what gets scrubbed. MXC's schema uses `process.env` exactly as given unless `inheritDefaultEnv` is set ([MXC schema 1.0.0](https://raw.githubusercontent.com/microsoft/mxc/main/schemas/stable/mxc-config.schema.1.0.0.json)).

Three Adeline details need specific handling. First, attachments can point at any user path through `file://` resource links (`turns.rs:445-492`). When a conversation is sandboxed, Adeline should embed the attachment or copy it into a temp directory the sandbox can read. Second, `kill_tree` uses `taskkill /T` on the direct child's pid (`platform.rs:164-196`). With a helper process in the middle, that only works if the sandboxed agent is a descendant of the helper, or dies with it. Codex documents that MXC creates the child suspended and assigns a kill-on-close job before resuming it ([codex mxc-sandbox README](https://github.com/openai/codex/blob/main/codex-rs/mxc-sandbox/README.md)), so killing the helper should take the agent down too. Still, `children_can_be_contained` (`platform.rs:530`) and `check_containment` (`scripts/engine-check/run_checks.py:343`) need sandboxed variants to prove it. Third, the headless build contains the whole engine, so sandbox code must live in `adeline_core` or `adeline_engine`, gated by `target_os`. A Cargo feature would not work here.

## Codex's MXC crate is the template; four other adopters show the pitfalls

Of the open source integrations, OpenAI's `codex-rs/mxc-sandbox` is the closest to what Adeline needs. It is Rust, and it routes a command through the current Codex executable directly into MXC's `BaseContainerRunner`. It never edits host ACLs, never creates users, and never asks for elevation ([codex mxc-sandbox README](https://github.com/openai/codex/blob/main/codex-rs/mxc-sandbox/README.md)). The launch core in `native.rs` makes three choices worth copying ([native.rs](https://github.com/openai/codex/blob/main/codex-rs/mxc-sandbox/src/native.rs)). It rejects the permissive learning-mode capability. It requires `supports_deny_paths()` before using deny lists. And it calls `spawn(request, …, StdioMode::Inherit)` without printing the SDK's diagnostic buffer, because that buffer can hold command or environment data. The typed request travels in launcher-only environment chunks (capped at 1,000,000 bytes, 4096-byte chunks) rather than on argv. Availability comes from a real create-and-close probe, not from OS build numbers. Codex's comment explains why: symbol presence "also succeeds on transitional Windows builds where MXC is not enabled" ([windows_mxc.rs](https://github.com/openai/codex/blob/main/codex-rs/sandboxing/src/windows_mxc.rs)). Codex pins the MXC crates to a git revision, and pins `tracelogging = "=1.2.3"` because a GNU toolchain issue breaks 1.2.4 ([codex-rs/Cargo.toml](https://github.com/openai/codex/blob/main/codex-rs/Cargo.toml)). Since then, Microsoft has published `mxc-sdk` 1.0.0 on crates.io with `v1::spawn`, `v1::spawn_with_pty` and a container lifecycle API ([docs.rs/mxc-sdk](https://docs.rs/mxc-sdk/latest/mxc_sdk/)). Adeline should try that public crate first, and fall back to Codex's internal-crate approach only if `mxc-sdk` lacks inherited-stdio spawning or the availability probe.

The other adopters each add a lesson. OpenClaw's plugin shells out to `wxc-exec.exe`. Its readiness check warns that `wxc-exec --probe` "can exit 0 even when detection fails", and it treats the reduced `appcontainer-*` tiers as working but weaker. It also checks that `ALL APPLICATION PACKAGES` can traverse `C:\`, because without that, `dir` fails inside the sandbox ([readiness.ts](https://github.com/openclaw/openclaw/blob/main/extensions/mxc/src/readiness.ts)). The same plugin documents that **ProcessContainer cannot enforce a read-only grant nested under a writable parent** ([openclaw mxc README](https://github.com/openclaw/openclaw/blob/main/extensions/mxc/README.md)). That directly limits protecting `.git/hooks` inside a writable project. It also flags microsoft/mxc#626: the Node SDK puts the whole request, secrets included, on `wxc-exec`'s argv. The in-process Rust route avoids that leak. VS Code's Copilot CLI integration maps settings into MXC-shaped path lists, but currently hard-codes `WINDOWS_SANDBOX_SUPPORTED = false`. It also drops host allowlists and fails closed, because the runtime "does not yet enforce them reliably everywhere" ([copilotcliSessionService.ts](https://github.com/microsoft/vscode/blob/main/extensions/copilot/src/extension/chatSessions/copilotcli/node/copilotcliSessionService.ts)). NVIDIA OpenShell's RFC moves all domain-level egress policy to a per-sandbox host CONNECT proxy on loopback. Its reason: "MXC network filtering is host/IP/CIDR-level" ([OpenShell RFC 0013](https://github.com/NVIDIA/OpenShell/blob/main/rfc/0013-native-windows-mxc/README.md)).

Real-world breakage is environmental rather than logical. The Codex tracker has open MXC failures caused by an unrelated locked BitLocker volume ([codex#50915](https://github.com/openai/codex/issues/50915)), by inaccessible mapped drives ([codex#52908](https://github.com/openai/codex/issues/52908)), by a deny entry under a missing parent ([codex#53576](https://github.com/openai/codex/issues/53576)), and by a Windows update ([codex#53417](https://github.com/openai/codex/issues/53417)). The lesson for Adeline is to show MXC error codes verbatim in the conversation status, not behind a generic "agent failed to start".

| Project | Integration | Granularity | When unavailable |
|---|---|---|---|
| Codex CLI | In-process Rust, self re-exec helper, `StdioMode::Inherit` | Per command; backend chosen per executor | Strict `mxc` fails hard; `prefer_mxc` falls back only at selection, "command failures never trigger backend fallback" ([README](https://github.com/openai/codex/blob/main/codex-rs/mxc-sandbox/README.md)) |
| OpenClaw | Shells out to `wxc-exec.exe` | Per command | Strict schema, no silent fallback; reduced tiers warn |
| VS Code Copilot CLI | MXC through the Copilot SDK | Per session config | Windows disabled; host lists fail closed |
| NVIDIA OpenShell | Rust driver over `wxc-exec`, host proxy | Per sandbox | RFC in review |
| Claude Code (native) | None on Windows; Seatbelt/bubblewrap elsewhere | Bash only | Runs unsandboxed unless `failIfUnavailable` ([docs](https://code.claude.com/docs/en/sandboxing)) |

## Five implementation options, ranked by cost and coverage

**Option A: pass agent-native flags.** This costs the least, but it leaves Adeline's most-used agent uncovered. Codex accepts `-c windows.sandbox=mxc` and `-c features.prefer_mxc=true` ([Codex Windows sandbox](https://learn.chatgpt.com/docs/windows/windows-sandbox)). Claude Code accepts `--settings '{"sandbox":{"enabled":true,"failIfUnavailable":true}}'` on macOS and Linux, and has nothing on native Windows. Even where it works, it leaves file tools, hooks and MCP servers outside the boundary ([Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing)). Adeline launches the ACP adapters `claude-agent-acp` and `codex-acp` (`crates/adeline_core/src/profiles.rs:72-75, 114-117`), not the CLIs. Nothing in the research confirms that either adapter forwards these flags or settings, so even this "cheap" option needs a spike. Microsoft lists Claude Code as "expected to follow" with MXC ([The Stack](https://www.thestack.technology/microsoft-takes-mxc-its-agent-management-layer-ga/)). That makes Option A the long-term path for agents that adopt MXC themselves, and argues for keeping the toggle semantic ("sandboxed") rather than tied to one mechanism.

**Option B: Adeline wraps the whole process with `mxc-sdk` and a self re-exec helper.** This is the recommended option. `Worker::start` swaps the program for `current_exe()` with a hidden `sandbox-exec` subcommand. The policy goes in the child environment, never in argv. The helper builds the MXC request and calls spawn with inherited stdio, so `spawn_piped`'s named pipes, the engine job and `std::process::Command` all stay as they are. The policy grants the project read-write, the agent install read-only, the agent home and temp read-write, and egress allowed while private CIDRs (10/8, 172.16/12, 192.168/16) are denied. The 1.0.0 schema can express that ([schema](https://raw.githubusercontent.com/microsoft/mxc/main/schemas/stable/mxc-config.schema.1.0.0.json)), and it matches Copilot CLI's default of "outbound internet on, local network off" ([GitHub Docs](https://docs.github.com/en/copilot/how-tos/cloud-and-local-sandboxes/using-local-sandboxing)). One SDK covers Windows, macOS (Seatbelt) and remote Linux engines (bubblewrap). The PTY gap in bubblewrap does not matter, because ACP runs over plain pipes ([copilotCli.ts](https://github.com/microsoft/vscode/blob/main/extensions/copilot/src/extension/chatSessions/copilotcli/node/copilotCli.ts)). The costs are real. Adeline owns a per-agent grant list. Granting `~/.claude` and `~/.codex` re-exposes the agents' tokens to the agent. And CIDR rules cannot express "only api.anthropic.com".

**Option C: shell out to `wxc-exec.exe`.** This is OpenClaw's route. It skips the SDK build, but Adeline must ship and locate a second binary. Secrets also risk leaking through the request path (mxc#626, [openclaw mxc README](https://github.com/openclaw/openclaw/blob/main/extensions/mxc/README.md)). It is useful as a one-day prototype to validate grants before Option B is written, and should not ship.

**Option D: containers or microVMs** (WSLC, Docker Sandboxes). These are rejected for now. MXC's VM backends are experimental on Windows, WSLC gives no stdin (`take_stdin` returns `None`, [docs.rs/mxc-sdk](https://docs.rs/mxc-sdk/latest/mxc_sdk/)), and paths and agent state would have to be remapped. **Option E**, running the engine in a VM, already works today through Adeline's remote engine (`docs/architecture.md:74-89`) and needs no new code.

| Option | Effort | Covers MCP, hooks, file tools | Windows Claude Code | Main risk |
|---|---|---|---|---|
| A. Native flags | 1-3 days plus adapter spike | No (Claude), partly (Codex) | No | Adapters may not forward flags; flags drift |
| B. `mxc-sdk` whole-process wrap | 1.5-2.5 weeks (Windows MVP) | Yes | Yes | Grant tuning; environmental MXC failures |
| C. `wxc-exec` shell-out | 2-4 days prototype | Yes | Yes | Extra binary; secret leakage |
| D. WSLC / microVM | Weeks | Yes | Yes | No stdin (WSLC), path remapping, experimental |
| E. Remote engine in VM | 0 | Yes | Yes | User manages the VM |

One interaction is still untested. If Adeline wraps `codex-acp` in MXC and Codex also tries to start its own MXC container for each command, the nested create may fail. Until a spike shows otherwise, the outer wrapper should run Codex with its own sandbox off. Treat this as an assumption to verify.

## Toggle placement: layered, resolved on the engine host, frozen per chat

Every surveyed product stacks the setting the same way: a global default, then project or session overrides, then a managed floor that can only tighten. The setting resolves on the execution host, as VS Code does for remote sessions ([VS Code agent sandboxing](https://code.visualstudio.com/docs/agents/run/agent-sandboxing)). That last point decides where Adeline's global toggle lives. It goes in `EngineSettings` (`crates/adeline_core/src/protocol.rs:236-241`), which is stored on each engine machine and broadcast as `Delta::Settings`. It does not go in the client-only `settings.yml` (`crates/adeline_core/src/config.rs:23-33`). A laptop UI connected to a remote Linux engine has to show that engine's capability, not its own.

| Layer | Where in Adeline | Strength | Weakness |
|---|---|---|---|
| Global | `EngineSettings` + `crates/adeline_ui/src/settings/engine.rs` | One switch per machine; matches the per-host capability probe | Too blunt: a "full access" Codex and a read-only reviewer get the same box |
| Per agent | `AgentDefinition` (`agents.rs:35-64`) + `agent_form.rs` | Adeline agents are user presets (harness + model + mode), so "Codex, full access, sandboxed" is a natural preset; grant lists differ per harness anyway | Duplicates the global switch unless it is three-state |
| Per conversation | `ExecutionConfig`, frozen at creation (`storage.rs:3-4`) | Lets a user run one risky task boxed; matches VS Code's per-session toggle | Changing it later means restart plus `session/resume`, which is untested for changed sandbox state ([Codex resume issue](https://claudeissues.com/issue/41629-agentic-dev-codex-exec-resume-inherits-stale-sandbox-mode-bypasses-fallback)) |

Recommended layering: **global default (off) → per-agent three-state (inherit/on/off) → resolved into `ExecutionConfig.sandbox` at creation**. Adeline already resolves model, effort and mode this way. A per-conversation override is a later addition to the new-chat flow, and it reuses the same field. Changing it on a live chat should go through the existing `Command::Restart` path plus resume, and only after a test confirms both adapters reload their sessions from inside the new boundary. Until then, offer "fork into a sandboxed conversation" instead. Two rules apply to every layer. First, if the sandbox was requested and the probe fails, refuse to start, and give the MXC reason and an explicit "start unsandboxed" action. Codex and OpenClaw both fail closed this way, while Claude Code's silent default fallback is the trap to avoid ([Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing)). Second, show the effective state in the chat header ("Sandboxed (MXC)", "Sandboxed (Seatbelt)"), not the requested one. Probes stay unsandboxed: they run in a fresh temp directory with MCP servers cleared. Logins stay unsandboxed too, because they have to write the credentials the sandboxed agent later reads.

Several facts limit what "sandboxed" can promise. ProcessContainer cannot deny a subpath under a writable project ([openclaw mxc README](https://github.com/openclaw/openclaw/blob/main/extensions/mxc/README.md)), and deny paths depend on OS support ([native.rs](https://github.com/openai/codex/blob/main/codex-rs/mxc-sandbox/src/native.rs)). So the protected-path list vendors rely on (`.git/hooks`, `.git/config`, `.vscode`, `.mcp.json`, agent config) cannot be guaranteed on every Windows build ([Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing)). Copilot CLI's docs add more caveats: sandboxed PowerShell on unpatched builds can report `C:\` as its working directory, and blocked paths that don't exist get created as directories ([GitHub Docs](https://docs.github.com/en/copilot/how-tos/cloud-and-local-sandboxes/using-local-sandboxing)). Under MXC, Codex also kills the remaining descendants when the foreground process exits, so detached dev servers die ([codex mxc-sandbox README](https://github.com/openai/codex/blob/main/codex-rs/mxc-sandbox/README.md)). The UI should state that "sandboxed" limits what the agent can reach. It does not mean the agent's output is safe to run on the host.

Phase 1's new code should come to roughly 400 to 700 lines across core and engine, plus UI wiring. ## Conclusion

Most harnesses had to retrofit sandboxing around their own tool loop. Adeline doesn't have to, because it never executes tools itself. That makes the agent process the natural and complete boundary, and lets Adeline sandbox Claude Code on Windows today, which Claude Code itself cannot do. The cost is that Adeline takes on policy work the agents used to own: grant lists per harness, an egress story MXC's CIDR-only schema cannot finish, and honest messaging when a Windows build cannot enforce deny paths. Build the wrapper as a bridge, not a moat. Keep the user-facing setting as "sandboxed: inherit/on/off", resolved on the engine host, so that once an adapter sandboxes itself natively with MXC, Adeline can hand that agent over to Option A without changing the UI or the stored conversations.

One question decides whether this is a two-week or a four-week project: does the public `mxc-sdk` let a helper inherit Adeline's existing named pipes? Answer it in the Phase 0 spike before any toggle UI is built.
